다음 새 사실과 기존 유사 사실 후보를 비교해, 어떻게 처리할지 JSON 객체로만 답해라.

새 사실:
  content: {new_content}
  memory_type: {new_type}
  event_time: {new_event_time}

기존 유사 사실 후보:
{candidates_block}

판단 기준:
- ADD: 완전히 새로운 정보(후보들과 의미가 충분히 다름).
- UPDATE: 기존 사실 중 하나의 상태/선호/사실이 자연스럽게 갱신됨(예: 이사, 직업 변경, 취향 변화). target_id에 어떤 사실을 갱신하는지 명시.
- CONFLICT: 기존 사실과 모순됨(과거 진술이 틀렸음을 시사). target_id 명시.
- NOOP: 기존 후보 중 하나와 사실상 같은 내용(중복). target_id 명시.

다음 중 하나의 형태로만 출력:
{{"action":"ADD","reason":"<짧은 설명>"}}
{{"action":"UPDATE","target_id":<기존 memory_id>,"reason":"<짧은 설명>"}}
{{"action":"CONFLICT","target_id":<기존 memory_id>,"reason":"<짧은 설명>"}}
{{"action":"NOOP","target_id":<기존 memory_id>,"reason":"<짧은 설명>"}}

JSON 객체만 출력. 다른 텍스트 금지.

추가 갱신 판단 계약 — 두 모델 공통:
- 유사도는 후보를 찾는 단서일 뿐, 같은 주제라는 이유만으로 UPDATE하지 않는다.
- UPDATE는 동일 대상의 동일 속성에 대해 새 정보가 현재 값을 대체하는 경우다. 다른 속성의 추가 설명, 새로운 사건, 별도 작업의 진행은 ADD다.
- 과거 경험과 최근 경험이 동시에 사실일 수 있으면 과거 사실을 틀렸다고 처리하지 않는다. 단순한 날짜 경과로 UPDATE/CONFLICT를 선택하지 않는다.
- CONFLICT는 동일 진술에 대한 명시적 오류 정정 또는 양립 불가능한 모순일 때다. 미래 계획의 날짜 변경과 과거 진술이 원래 틀렸다는 정정을 구분한다.
- NOOP는 의미상 같은 사실이고 새 정보가 없을 때다.
- UPDATE/CONFLICT는 기존 행 전체를 만료시키는 저장 동작으로 이어진다. 새 사실이 기존 행의 별개 유효 정보를 보존하지 못한다면 이 단계에서 내용을 새로 합성하지 말고 ADD로 공존시킨다. 후속 구조 개선 전의 보수적인 동작이며 별도 중복 검증이 필요하다.
- ADD 이외에는 제시된 후보의 memory_id만 target_id로 반환한다. 대상이 불명확하면 임의 ID를 선택하지 않는다.
- 출력 키와 action 종류는 위 원래 계약을 그대로 따른다. reason은 짧은 판정 이유만 쓴다.

판단 요약: 같은 사실이면 NOOP, 동일 속성의 현재 값 변경이면 UPDATE, 명시적 오류 정정이면 CONFLICT, 별개 사실이면 ADD. JSON 하나만 출력한다.
